## 0. Findings that shape the design

### 0.1 Server Actions and the proxy (local disposable tests, Next.js 16.4.6)

These tests used a throwaway two-page app (`/login` and `/platform/login`, each with its own action), with the
app's exact `proxy` matcher.

| # | Probe | No host check | With a proxy host check |
|---|---|---|---|
| T1 | the console action POSTed to `/login` on the customer host | **the console action ran** (forwarded internally) | blocked: the forwarded request re-entered the proxy as `/platform/login` with the original `X-Forwarded-Host` |
| T2 | the customer action POSTed to `/platform/login` on the admin host | **the customer action ran** | blocked (same mechanism) |
| T3/T4 | each action on its own page and host | ran | ran (no regression) |
| T6 | the action of a **dynamic** console page POSTed to `/platform/c/abc.png` on the customer host | ran | **still ran**: the matcher excludes `*.png`, so the proxy never saw the request |

**Conclusions:**
- Next.js forwards an action whose ID the current page doesn't own as a new internal request to
  `__NEXT_PRIVATE_ORIGIN + <owning page>`. The original headers go with it (`set-cookie` and hop-by-hop headers
  are dropped).
- A proxy-level host check therefore does catch forwarded actions, but **the proxy alone is not enough.**
- A host check is needed **at the server-side entry points**, and the matcher must not let action requests skip
  the proxy.

| `CUSTOMER_APP_HOST` | `<CUST_HOST>` | `<CUST_HOST>` (identical) |
| `PLATFORM_TRUSTED_PROXY_HOPS` | `1` (nginx overwrites `X-Forwarded-Host`) | `1` |
| `PLATFORM_CONSOLE_ENABLED` | `true` from F1 | **unset** |

| `NODE_ENV` | `production` | `production` |

- Both host variables are set together, or neither. Only one set, an invalid value, two equal values, an IP
  address or a malformed hop count make **both** surfaces refuse every request (fail closed). The process never
  falls back to unbound.
- Unbound (neither set) behaves exactly as before. That is the live ERP's configuration, and it is unchanged.
- **Configuration.** Two new variables, set together: `PLATFORM_CONSOLE_HOST` and `CUSTOMER_APP_HOST`, each the
  exact lower-case host (with `:port` only for local tests).
  - Neither set (as on the live ERP today): behaviour is unchanged.
  - Both set and valid: the binding below applies.
  - Anything else: both surfaces refuse (fail closed).
  - **As implemented, binding is opt-in by configuration.** It is not forced whenever `PLATFORM_CONSOLE_ENABLED=true`,
    because the existing suites run the console unbound. Staging therefore **must** set both variables. S7 checks both
    env files for them before any unit starts, and S9's R-tests prove the binding is active. Making the binding
    mandatory whenever the console is enabled in production is a follow-up for the Option B release (K6).
- **Addressed host.** One shared, edge-safe helper. It uses the same rule as `assertSameOrigin`: the single
  `X-Forwarded-Host` when `PLATFORM_TRUSTED_PROXY_HOPS` ≥ 1, otherwise `Host`; lowercased; a comma list is refused.
- **Proxy.**
  - A `/platform` path on any host other than the console host → 404 with noindex.
  - Any other path on the console host → 404.
  - A matcher entry so that **every request with a `Next-Action` header runs the proxy**, whatever its suffix.
- **Console server side (defence in depth).**
  - `assertSameOrigin` also requires the addressed host to equal `PLATFORM_CONSOLE_HOST`.
  - `authorizePlatformToken`'s request wrappers and `signInCore` refuse on any other host.
  - This covers every console action and route handler, including requests that skip the proxy (T6).
- **Customer server side.** These all refuse when the addressed host equals `PLATFORM_CONSOLE_HOST`:
  - the customer session helpers (`requireSession`, `getSession`);
  - the customer login and register actions;
  - the invitation-acceptance actions;
  - the customer route handlers (`/api/*`, `/uploads/*`, `/print/*`, the exports).
  - The loopback `PDF_RENDER_ORIGIN` host is not the console host, so PDFs keep working.
- **Tests, both directions.**
  - Unit tests of the helper.
  - A verification script that repeats T1, T2, T3/T4 and T6 against the real app for **both** directions.
  - The customer regression run with the variable unset, to prove the live ERP is unaffected.
- **In staging both env files set it.** The customer process also has the console switch off, so it refuses the
  console on two independent grounds.

### 0.3 Localhost-only is not isolation on this VPS

Several loopback TCP services accept connections without credentials. A **network namespace does not hide
filesystem unix sockets**, and several world-writable ones exist (database servers, a scanner control socket,
the system bus, the DNS resolver's varlink socket, and other applications' sockets in `/tmp`). The details are in
the private evidence.

The design therefore combines:
- the namespace `<NS>`, for TCP;
- an **allow-list filesystem view** (§B.2), for unix sockets and files.

`elite-po-admin-proxy.socket` / `.service` (the customer pair is identical, with the customer ports):
~~~ini
# .socket
[Socket]
# Unix-domain, not host TCP: on a shared VPS any local process can reach a loopback port, bypassing nginx (Basic
# Auth, the X-Forwarded-Host overwrite). Only nginx can open this socket.
ListenStream=<ADMIN_SOCK>
SocketUser=root
SocketGroup=<NGINX_GROUP>
SocketMode=0660
DirectoryMode=0750
[Install]
WantedBy=sockets.target

# .service
[Unit]
Requires=elite-po-admin.service
After=elite-po-admin.service
[Service]
ExecStart=/usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:<ADMIN_IN>
NetworkNamespacePath=/run/netns/<NS>
DynamicUser=yes
Slice=elite-po-staging.slice
MemoryMax=64M
# + the same sandbox block as above, minus the Bind*/ReadWrite lines
~~~

- This is the documented pattern: the socket is listened on in the host's namespace, while the proxy runs
  inside `<NS>`.
- nginx → Unix socket → proxy → app. The app sees peer `127.0.0.1`. **Direct upstream access is restricted:** there is no host TCP listener at all; the socket is `0660` for `<NGINX_GROUP>` only, so no other local process can reach the apps or forge `X-Forwarded-Host` (the apps trust exactly one proxy hop).
- The client address comes from `X-Forwarded-For`: nginx sets it to `$remote_addr`, and the app is set to
  `PLATFORM_TRUSTED_PROXY_HOPS=1`.

### B.2 Network isolation

**What the namespace gives (`<NS>`):**
- only `lo`: no route, no DNS server, no access to the host's loopback services;
- the abstract unix sockets of `<NS>` are its own.

**What the filesystem view gives (B.1):**
- `/run` (with `/var/run`), `/var/lib`, `/var/spool`, `/srv`, `/var/www`, `/opt` and `/home` are hidden, apart
  from the bound paths;
- `PrivateTmp` hides other applications' sockets in `/tmp`.

**The same rules cover every process that touches `<DB>`:**
- the two apps and the two proxies;
- the backup dump unit;
- **every operator or owner command** — migrations, `platform:db:check`, `verify:db-hardening`, bootstrap,
  probes, restore.
- Those commands run only through `/usr/local/sbin/elite-po-run`. It calls `systemd-run --pty --wait --collect`
  with `--uid=<APP_USER>`, `--slice=elite-po-staging.slice`, `-p NetworkNamespacePath=/run/netns/<NS>`, the
  identical sandbox property list, and `-p EnvironmentFile=` for the chosen env file.
- Database passwords for operator roles are passed with `LoadCredential=` (never on a command line).
- Connecting to `<DB>` any other way is a stop condition.

**Neon is unreachable on three independent grounds:**
- there is no route or DNS inside `<NS>`;
- no Neon credential exists on the staging side;
- the PO-06 `local-db-guard` refuses any non-loopback or non-`_test_only_` target before connecting.

**V-NET: the isolation probe.** It runs at S8 (tool path) and at S9 (inside each app unit, via
`systemd-run -p` with the unit's properties, compared with `systemctl show`). It must show:
1. TCP to **every** host-loopback port in the S0 snapshot (other applications, database servers, caches, PHP
   pools, the ERP): refused. Only `<PG_PORT>`, `<ADMIN_IN>` and `<CUST_IN>` answer.
2. Every filesystem unix socket path in the S0 snapshot: `ENOENT` or `EACCES`.
3. DNS (`getent hosts` for a public name and for a Neon-style name): fails.
4. TCP to a public address on 443 and 5432: network unreachable. Node `fetch` to a public URL: fails.
5. The guard with a non-loopback `DATABASE_URL`: exit 2, refused before connecting.

**Cluster-only config:** `/etc/postgresql/16/<CLUSTER>/conf.d/10-staging.conf`:
- `listen_addresses='127.0.0.1'` (inside `<NS>`);
- `external_pid_file='/run/elite-po-pg/16-<CLUSTER>.pid'`;
- `ssl=off`. The cluster user cannot read the shared snakeoil key, and traffic never leaves the namespace's
  loopback;
- `shared_buffers=64MB`, `max_connections=30`, `password_encryption=scram-sha-256`.

**`pg_hba.conf` (this cluster only):**
- `local all <PG_USER> peer`;
- `host <DB> <OWNER_ROLE>,<APP_ROLE>,<BACKUP_ROLE> 127.0.0.1/32 scram-sha-256`;
- nothing else.

**Drop-in** `postgresql@16-<CLUSTER>.service.d/10-staging.conf`:
- `Requires=` / `After=elite-po-staging-netns.service`;
- `NetworkNamespacePath=/run/netns/<NS>`;
- `Slice=elite-po-staging.slice`;
- `PIDFile=/run/elite-po-pg/16-<CLUSTER>.pid`;
- `MemoryMax=384M`, `CPUQuota=30%`.

**Rules:**
- Start and stop it only with `systemctl start|stop postgresql@16-<CLUSTER>`.
- **Never** use the umbrella `postgresql.service`, which acts on every cluster.
- **Never** call `pg_ctlcluster` directly: it would run outside `<NS>`.

**Rehearsal risk.** If `pg_ctlcluster` refuses the non-default socket and PID directory, stop. The only fallback
is the standard Ubuntu multi-cluster layout under the `postgres` OS user. It keeps config, data, roles and port
separate, but needs the owner's sign-off. Never fall back to a database inside `main`.

**Guard compatibility.** Inside `<NS>`, `127.0.0.1:<PG_PORT>` is the server address, and `listen_addresses` is
loopback only. Every `local-db-guard` and bootstrap target check passes.

**Roles.**
- `<OWNER_ROLE>`: the migration and owner role, used only through `elite-po-run`.
- `<APP_ROLE>`: DML only, used at runtime.
- `<BACKUP_ROLE>`: read-only, for dumps.
- As in `po06/STAGING_ENV_TEMPLATE.md` §5. No superuser at runtime.

## C. Hostname routing and application binding

**Both vhosts.**
- Only the two new CloudPanel sites are edited.
- Headers forwarded: `Host $host`; `X-Forwarded-Host $host`; `X-Forwarded-Proto https`.
- **`X-Forwarded-For $remote_addr`**, which overwrites the template's `$proxy_add_x_forwarded_for`. The customer
  code reads the leftmost entry, which a client could forge.
- Port 443 only.
- `X-Robots-Tag: noindex, nofollow` and a deny-all `robots.txt` from nginx.
- CloudPanel Basic Auth, with `.well-known` exempt.

| `<ADMIN_HOST>` → `proxy_pass http://unix:<ADMIN_SOCK>:` | `<CUST_HOST>` → `proxy_pass http://unix:<CUST_SOCK>:` |
|---|---|
| `= /` → 302 `/platform/login`; proxy `= /platform`, `^~ /platform/`, `^~ /_next/static/`, `= /favicon.ico`; everything else 404 | `= /platform` and `^~ /platform/` → 404; everything else proxied (customer pages, `/register/accept`, `/join/accept`, `/api/*`, `/print/*`, `/uploads/*`, `/assets/*`, exports, `/_next/static/*`) |

**The app side** (both env files):
- `PLATFORM_CONSOLE_HOST=<ADMIN_HOST>` (H-1);
- `CUSTOMER_PUBLIC_ORIGIN=https://<CUST_HOST>`;
- `PLATFORM_TRUSTED_PROXY_HOPS=1`;
- `NODE_ENV=production`, so the cookies are `__Host-` with no `Domain`;
- `PDF_RENDER_ORIGIN=http://127.0.0.1:<CUST_IN>` in `customer.env` only. It stays unset in `admin.env`, as in the §0.2
  table: PDFs are a customer surface, and the loopback origin is never accepted as the console host.

**The console switches** (`PLATFORM_CONSOLE_ENABLED`, `PLATFORM_INVITATIONS_ENABLED`,
`PLATFORM_USER_INVITATIONS_ENABLED`) appear **only in `admin.env`**. `TENANT_ACCESS_ENFORCEMENT` and the

### F.1 S6 on the VPS: what was measured, and why the build moved off it (23 Nov 2026)

`npm ci` then `next build` of `<APPROVED_SHA>` (Next.js 16.4.6, Turbopack), as `<APP_USER>` in a capped transient
unit outside the slice, monitored every 10 s against §I. Each attempt was stopped by its own limit or by the monitor;
no shared service was affected (the ERP's PID and health unchanged, every §I check held).

| Attempt | Limits | Result |
|---|---|---|
| 1 | the plan's: `MemoryMax=1536M`, swap allowed | at the cap during the compile, the build pushed **host swap up by 300 MB**; the §I guard (swap growth > 256 MB) stopped it. MemAvailable never below 3.7 GB; the swap returned |
| 2 | `MemorySwapMax=0`, `MemoryHigh=1280M`, Node heap 1024 MB | held at the soft limit and throttled by reclaim for the **full 60-minute limit** (16 minutes of CPU), never finished compiling; **timed out**. Swap flat, MemAvailable ≥ 3.8 GB |
| 3 | `MemoryMax=2304M`, no soft limit, `MemorySwapMax=0`, Node heap 1536 MB | compiled in 60 s, then **killed by the kernel inside its own limit** (`CONSTRAINT_MEMCG`) during "Running TypeScript", peak 2284 MB. Swap flat, MemAvailable ≥ 3.1 GB |

**Off-VPS measurement** (GitHub-hosted Ubuntu 24.04, the same Node.js 22.23.2 and commit, limited to 2 CPUs as on
the VPS; four runs): 42–81 s; largest single process 2.0–2.1 GB resident; all build processes together 2.6–3.3 GB at

about 5.1 GB available; §I stops every stage below 2.5 GiB. That leaves at most about 2.5 GB, shared with every other
service, and the build does not fit in it. Raising the limits would spend the shared services' safety margin on a
build: rejected (S6-R1). The build moved to an adequately resourced, isolated runner. The VPS only receives a verified
archive (S6-R, §N), and type checking stays mandatory.

**State left on the VPS (until S6-R):** S1–S5 as listed in the status above, intact. The incomplete output of
attempt 3 (`.next`, `node_modules`) and the npm cache in the build user's home remain in `<APP_DIR>`. S6-R records them,
then removes them. The STOP record stays until the next written authorization.

## G. Backup and recovery (corrected per D-B1)

**Daily dump.** `elite-po-backup.service` / `.timer`, daily at a quiet hour.
- It runs inside `<NS>`, as `<APP_USER>`, in the sandbox.
- `pg_dump -Fc` of `<DB>` as `<BACKUP_ROLE>`, a tar of the fake-storage directory, and a row-count sidecar.
- The output is encrypted with `gpg --encrypt` to the **owner's public key only**, using a dedicated keyring of
  the public key alone.
- It is written to `/var/lib/elite-po-staging/backups/` (`0700`). **The VPS never holds the private key.**

**Retention:** 14 daily copies on the VPS. The off-host copy is kept 14 days by the target's lifecycle rule.

**Off-host copy (owner decision D-B2: dedicated object storage).** `elite-po-offsite.service` / `.timer`, after
the dump.
- It runs outside `<NS>`, because it needs the internet, and has **no** database access: it only reads the
  encrypted files.
- It uses an owner-owned object-storage bucket via `rclone` (already installed), with a key limited to that bucket
  and **without delete permission**, plus a 14-day lifecycle rule or object lock.
- **Pending:** the owner chooses the provider, creates the bucket and key, and enters the key privately on the host
  (root-only `0600`, never through an AI session). Until then S12 cannot run.

**Restore verification, before staging acceptance.**
- The owner fetches one off-host copy and decrypts it **on the PC** (the private key never leaves it).
- They stream it with `gpg -d … | ssh … 'sudo elite-po-run --restore …'` into a fresh `<DB>`-style
  `*_test_only_*` restore database.
- The restored row counts must match the sidecar.
- Then drop the restore database.

**Rebuild path.** The fictional data can always be recreated: manifest `--base`, then a new bootstrap.

**Code.** The previous build directory is kept for rollback.

## I. Stop conditions (apply at every stage)

Stop immediately, then run that stage's rollback (§J), if any of these happens:
1. The PID of `<ERP_UNIT>` changes, or it is not `active`.
2. Any unit that was `active` at S0 is no longer `active`.
3. Any existing vhost checksum changes, or `main`'s `postgresql.conf` or `pg_hba.conf` checksum, or `main`'s PID.
4. Any new TCP listener appears on the host, or a Unix socket other than `<ADMIN_SOCK>` / `<CUST_SOCK>`, or either socket is not `0660 root:<NGINX_GROUP>` (S9 and later).
5. `MemAvailable` falls below 2.5 GiB, swap use grows by more than 256 MiB within a stage, 1-minute load
   stays above 1.8 for 5 minutes, or free disk falls below 25 GB.
6. Any V-NET or V-SBX probe that should fail succeeds.
7. The guard, `--check`, `--status` or any migration step exits non-zero.
8. Any R-test fails, or any `<ERP_HOST>` public check (status, headers, certificate fingerprint) differs from
   S0.

## J. Rollback procedure (reverse order; each step stands alone; none touches the ERP)

1. **Switches:** off, F7 → F1. Restart only the staging units.
2. **Sites:** delete the two CloudPanel sites (vhost, certificate, Basic Auth). Run `nginx -t`. Confirm the
   existing vhost checksums are unchanged.
3. **DNS (owner):** delete the two A records.
4. **Timers and services:** `systemctl disable --now` the backup and off-host timers, both proxy sockets and
   both app units. Remove their unit files. Run `daemon-reload`.
5. **Database:** `systemctl stop postgresql@16-<CLUSTER>`, then `pg_dropcluster 16 <CLUSTER>`. Remove the drop-in
   and the tmpfiles entry. Verify `main` (PID and checksums).
6. **Namespace and slice:** `systemctl disable --now elite-po-staging-netns.service`. Remove the unit, the slice
   and `elite-po-run`.
7. **Files and users:** remove `/etc/elite-po-staging`, `/var/lib/elite-po-staging` (after the owner has kept any
   backup wanted) and `<APP_DIR>`. Then `userdel <APP_USER>` and `<PG_USER>`.
8. **Final check:** compare everything with the S0 baseline.
