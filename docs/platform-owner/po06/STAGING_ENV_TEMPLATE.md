# PO-06 — Staging configuration template (variable NAMES only)

**Status:** preparation only. Nothing here was provisioned, generated, stored or transmitted. No value below is real.
Angle-bracket entries are placeholders the owner fills **at provisioning time, on the staging host only**. This file is
deliberately not named `.env*`. A filled-in copy must never be committed, pasted into a ticket or chat, attached to a
screenshot, or copied to any production system.

The inventory is complete. It is every `process.env` name read by `src/` and `scripts/`, found by searching for
`process.env.X`, `env.X` and `process.env[...]`. `verify/verify-po06-staging-readiness.mts` checks this file against the
code, so a name added to the code without a row here fails the readiness check.

## 1. Rules for every secret

| Rule | How |
|---|---|
| Generated on the staging host, by the owner or an operator the owner names | the command in the table, run in an interactive root shell with history disabled (`set +o history`) |
| Never reused | no staging secret equals a production, development or CI secret, and no two staging secrets are equal. `PLATFORM_AUTH_SECRET` must differ from `AUTH_SECRET`: the application refuses to start otherwise |
| Stored once, root-only | `/etc/elite-erp-staging/app.env`, mode `0600`, owner root. The systemd unit reads it with `EnvironmentFile=`. It lives outside the repository and outside any backup directory, and the application user cannot read the file itself |
| Escrowed separately | `FIELD_ENCRYPTION_KEYS` (every version) and `AUTH_SECRET` also go into the owner's password manager. Without them a restored backup cannot be decrypted (`docs/security/backup-dr.md`) |
| Never printed | no `echo`, no `env` dump, no shell history, no log line, no screenshot. Connection strings are never passed on a command line other users can see: use `PGPASSFILE` or a service file |
| Rotated by replacement | a new value in the env file, then a restart. For `FIELD_ENCRYPTION_KEYS`: prepend `2:<new>`, keep `1:<old>` until every row is re-encrypted |

## 7. Generating and storing the secrets — the procedure (Prompt 7, after approval; not done here)

1. Open an SSH session to the approved staging host and become root. Run `set +o history; umask 077`.
2. Create `/etc/elite-erp-staging/` (`0700`, root) and an empty `app.env` (`0600`).
3. Generate each secret with the command in §2 **directly into the file**, for example:
   `printf 'AUTH_SECRET=%s\n' "$(openssl rand -base64 48)" >> /etc/elite-erp-staging/app.env`. Never echo a secret to the terminal.
4. Generate the database role passwords the same way. Write them only into the pgpass files of §5.
5. Copy `AUTH_SECRET` and `FIELD_ENCRYPTION_KEYS` into the owner's password manager over the SSH session (for example,
   `cat` into a local secure prompt). Then clear the terminal scrollback.
6. Generate the backup key pair **offline, on the owner's machine**. Copy only the public key to the host. Import it
   into `GNUPGHOME` and set its ownertrust. The private key stays offline (password manager or hardware token).
7. The first Platform Owner administrator is created interactively with `npm run platform:bootstrap` on the host. The
   bootstrap accepts only a loopback `*_test_only_*` database, which is why the staging database is named that way. It
   asks for the administrator's e-mail address and password; the password is typed and never echoed. It then prints
   the TOTP enrolment secret and the recovery codes **once**, to the operator's own terminal. They go straight into the
   owner's password manager.
8. Record in the deployment log that each secret exists — never its value — then close the session.
